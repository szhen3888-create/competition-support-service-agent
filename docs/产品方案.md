# 竞赛辅助服务智能体 — 产品方案

> 版本：v1.0  
> 更新日期：2026-10-26  
> 需求来源：竞赛辅助服务智能体应用开发（预算 ¥1500，截止 2026-12-31）

---

## 1. 产品定位

面向**计算与智能技术学院**的「竞赛全生命周期」助手，服务三类用户：

| 角色 | 核心场景 |
|------|----------|
| 学生 | 查竞赛、匹配推荐、生成备赛计划 |
| 教师 | 材料初审、修改建议、答辩预演题 |
| 管理员 | 台账统计、可视化、导出报表 |

**设计原则（对应需求书「其他注意事项」）：**

1. **政策/规则 → RAG + 原文引用**，无证据则拒答  
2. **统计/台账 → 结构化 SQL + Pandas**，禁止纯靠 LLM 编数字  
3. **知识与规则外置**，新竞赛/新政通过导入配置扩展，不硬编码  

---

## 2. 总体架构

采用 **「意图路由 + 双通道」**：

```
用户（Vue）
    ↓ SSE 流式
FastAPI 网关（鉴权 / 会话 / 限流）
    ↓
LangGraph 主编排
    ├─ 意图分类
    ├─ 知识通道：Agentic RAG（检索→评分→改写→生成+引用）
    ├─ 业务通道：工具调用（SQL / 文档生成 / 导出）
    └─ 写作通道：预算/借款/报销/备赛计划（模板+结构化字段）
         ↓
   MySQL（业务台账）  +  向量库（知识片段）  +  对象存储（原文文件）
         ↓
   LLM Provider 抽象层（默认 DeepSeek，可切换 Qwen / 豆包 / 任意 OpenAI 兼容 API）
```

**为何双通道：**  
需求明确要求「竞赛统计必须基于结构化业务数据」「政策不能仅靠 LLM」。把「查政策」和「算数据」拆开，是交付验收与测试报告能否过关的关键。

## 3. 功能与 Agent 映射

| # | 需求 | 实现方式 | 主工具 |
|---|------|----------|--------|
| 1 | 竞赛知识问答 | Agentic RAG + 强制引用 | 向量检索 / 元数据过滤 |
| 2 | 竞赛推荐 | 学生画像 + 竞赛库匹配 + LLM 解释 | SQL + 推荐 Prompt |
| 3 | 备赛辅助 | 抽取要求 → 计划/任务清单 | RAG + 结构化输出 |
| 4 | 项目指导辅助 | 材料上传 → 清单校验 → 建议/答辩题 | 文档解析 + LLM |
| 5 | 预算申请辅助 | 奖项/人数/地点等填表 → 预算明细稿 | 模板引擎 + LLM |
| 6 | 借款辅助 | 已批预算 + 竞赛信息 → 借款说明 | 模板 + SQL |
| 7 | 报销辅助 | 票据信息整理 + 材料完整性检查 | 规则校验 + LLM |
| 8 | 数据统计 | 按年/类型/专业/师生/奖级聚合 | SQL + Pandas |
| 9 | 可视化分析 | 参赛/获奖/指导量图表 | ECharts 配置下发 |
| 10 | 结果导出 | Excel/Word | openpyxl / python-docx |

**LangGraph 节点建议：**

```
START → classify_intent
  ├ knowledge_qa   → retrieve → grade → [rewrite?] → generate(+citations)
  ├ recommend      → query_competitions → rank → explain
  ├ prep_assist    → extract_requirements → plan_tasks
  ├ review_assist  → parse_upload → checklist → suggestions
  ├ finance_assist → collect_slots → fill_template → draft
  ├ stats_query    → nl2sql/tool → pandas → chart_spec
  └ export         → build_file → return_url
→ END
```

控制面（意图、打分、改写）用小/快模型；长文生成用主力模型。

## 4. 技术选型

| 层级 | 选型 | 说明 |
|------|------|------|
| LLM | DeepSeek（默认）/ Qwen / 豆包 | 通过统一 Provider 抽象，OpenAI 兼容 API |
| Agent | LangGraph StateGraph | 条件边、检查点、SSE 按节点推进度 |
| RAG | 混合检索（向量 + BM25）+ 重排 | 竞赛名、截止日期等关键词更准 |
| Embedding | bge-m3 / 通义 text-embedding | 中文竞赛文档效果好 |
| 向量库 | Chroma（默认）或 pgvector | 预算紧、部署简单 |
| 业务库 | MySQL 8 | 竞赛台账、用户、会话、文件元数据 |
| 后端 | Python 3.11 + FastAPI | 异步、SSE、OpenAPI |
| 前端 | Vue 3 + Vite + Element Plus + ECharts | 问答 / 知识库 / 分析 |
| 文档解析 | PyMuPDF + python-docx + openpyxl | PDF/Word/Excel 入库 |
| 部署 | Docker Compose | api + web + mysql + chroma |

## 5. 数据设计

### 5.1 核心业务表

- `users`：角色（student / teacher / admin）
- `competitions`：名称、级别、类别、专业方向、年级要求、报名截止…
- `competition_awards`：奖项设置与奖金标准
- `participations`：学生参赛记录（年、项目、指导教师、结果）
- `budgets` / `loans` / `reimbursements`：财务草稿与状态
- `documents`：知识库原文元数据
- `chunks`：分块文本 + document_id + 页码/段落

统计、推荐、导出一律走这些表；LLM 只做「自然语言 → 查询参数 / 文案润色」。

### 5.2 知识库治理

- 支持 PDF / Word / Excel 导入，元数据：竞赛名、年份、文档类型、阶段
- 分块保留页码与段落；表格可「整表 + 行级」双粒度
- 同文档多版本只保留 active 参与检索
- 回答格式：结论 + `[来源：文件名 p.x]`；检索不足则拒答

## 6. 前端信息架构

1. **智能对话页**（主入口）：角色切换、流式回答、引用卡片
2. **知识库管理**：上传、解析状态、启用/停用
3. **竞赛台账**：竞赛 CRUD、参赛/获奖录入
4. **数据分析**：筛选器 + ECharts + 导出
5. **材料工作台**：申报书初审 / 预算借款报销草稿

## 9. 风险与对策

| 风险 | 对策 |
|------|------|
| LLM 编造政策/数据 | 统计强制走 SQL；问答无命中则拒答 |
| 中文竞赛专名检索差 | 混合检索 + 元数据过滤 |
| Agent 死循环 | 最大迭代 2～3；超时降级 |
| 工期紧 | 单一主 Agent + 工具集；向量库用 Chroma |
| 后续加竞赛 | 全部配置化入库，禁止硬编码 |

---

## 10. 当前开发约定

- **默认 LLM**：DeepSeek API（`https://api.deepseek.com`）
- **可切换**：后台通过环境变量 / 配置接口切换任意 OpenAI 兼容 API（Qwen、豆包等）
- **密钥**：仅存 `.env`，不入库、不提交 Git
